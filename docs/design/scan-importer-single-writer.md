# Scan importer: ผู้เขียนคนเดียว + กักแถวย้อนหลัง

สถานะ: **ออกแบบ + แกนตรรกะล้วนเสร็จ (8 พ.ย. 2569)** — ยังไม่เขียนฐานข้อมูลจริง (รอบัญชีเขียน MariaDB ที่จำกัดสิทธิ์เฉพาะ `fingle_scan` และการอนุมัติจาก HR)
ที่มา: เหตุการณ์ 8 พ.ย. 2569 ใน `docs/design/lost-scan-and-importer.md` · การตัดสินใจ: `docs/adr/0002-scan-importer.md` ข้อ 5–10
โค้ด: `finger_scan_notify/scan_importer/plan.py` (`plan_batch`, `plan_release`) · test: `tests/test_scan_importer_plan.py`

## ปัญหาที่ต้องแก้
1. **ผู้เขียนสองราย** เขียนแถวจากเครื่องสแกนลง `fingle_scan`: ตัวนำเข้าเดิม (`CWSMservice32.exe`, เก็บ `CommitTime` ถึงวินาที) และ `SCAN-WATCH` ของ HOSOffice ERP (เก็บ `TimeInout` ระดับนาที)
   ต่างกันที่ความละเอียดของเวลาและกันซ้ำด้วยเวลา จึงไม่เห็นแถวของกันและกัน → แถวซ้ำ (60 วัน: 767 กลุ่มคู่กับ SCAN-WATCH + 733 กลุ่มแถวเดิมซ้ำ)
2. **ไม่มีเบรกกันของเก่า:** หลัง restart SCAN-WATCH เติมสแกนย้อนหลัง 18 เดือนครั้งเดียว (6,564 แถว) และผู้แจ้งเตือนส่งการ์ดตามทุกใบ
3. ตัวนำเข้าเดิมดึงเฉพาะแถวล่าสุดและกันซ้ำด้วยเวลา จึงทำสแกนที่ใกล้กันหาย (Lost scan)

## หลักการ
- **ผู้เขียนรายเดียว:** มีเพียง Scan importer ตัวใหม่ที่เขียนแถวที่มี Device sequence ; ตัวเดิมและ SCAN-WATCH หยุดเขียน (SCAN-WATCH ปิดแล้ว และแอปแจ้งเตือนเฝ้า `unexpected_writer` ถ้ามันกลับมา)
- **กุญแจ = (`MACHIN_ID`, `MACHIN_SCAN_ID`)** ไม่ใช่เวลา: เขียนซ้ำเลขเดิม = ไม่เขียน (`INSERT … ON DUPLICATE KEY` ไม่เขียนทับ) ; unique index ใส่หลังล้างแถวซ้ำเดิม
- **เวลาที่เก็บ = `CommitTime`** (ถึงวินาที ตรงกับแถวของตัวนำเข้าเดิมซึ่งเป็นแถวส่วนใหญ่ — 35,033 แถวตั้งแต่ ID 300000 — และเรียงเข้า-ออกในนาทีเดียวกันได้ถูก) สำรองด้วย `TimeInout` เมื่อ CommitTime ว่าง
- **ป้ายผู้เขียน:** `CREATE_BY='SCAN-IMPORTER'` (ปกติ) และ `'SCAN-IMPORTER-RELEASED'` (ปล่อยจากที่กัก) ให้ระบบอื่นแยกแถวย้อนหลังออกได้
- **ไม่เดา:** ไม่มีจุดล่าสุดที่บันทึกไว้ = หยุดรอคน ไม่เริ่มจากต้นตาราง

## วงจรต่อรอบ (ทุก ~2 วินาที)
1. อ่านต้นทาง `WHERE ID_TimeInout > จุดล่าสุด ORDER BY ID_TimeInout` เป็นชุด (SELECT อย่างเดียว ใช้ `tigersoft` เดิม)
2. อ่านกุญแจที่มีอยู่แล้วใน `fingle_scan` ของเลขช่วงนั้น (ข้อควรระวัง: `MACHIN_SCAN_ID` **ไม่มีดัชนี** ให้อ่านด้วยช่วงเวลา/ID ที่ใช้ดัชนีได้ ห้าม join/EXISTS ซ้อน)
3. `plan_batch(rows, existing_keys, now, checkpoint=…)` → `insert / held / duplicate / flood / needs_baseline / next_checkpoint`
4. เขียน `insert` ใน transaction เดียว ; บันทึก `held` ลงที่เก็บของ importer ; แล้วค่อยขยับจุดล่าสุดเป็น `next_checkpoint` (ขยับหลังบันทึกสำเร็จเท่านั้น)
5. `flood` หรือมี `held` ใหม่ หรือ `needs_baseline` → แจ้ง IT (ครั้งเดียวต่อเหตุการณ์) ด้วยกลไกเดียวกับ `scanwatch`

## ตัวป้องกัน 4 ชั้น
| ชั้น | กติกา | กันเหตุการณ์ใด |
|---|---|---|
| 1 | ไม่มีจุดล่าสุด → ไม่เขียนอะไร รอคนตั้งจุดเริ่ม (`needs_baseline`) | จุดหายตอน restart แล้วเติมทั้งตาราง |
| 2 | แถวเก่ากว่า 24 ชม. เวลาไม่ชัด หรือล้ำอนาคตเกิน 1 ชม. → **กัก** (`held`) ไม่เขียนเอง ; แถวไม่มีเวลาสแกนปล่อยไม่ได้ (`unreleasable`) | เติมย้อนหลังหลัง restart/เครื่องสแกนออฟไลน์ |
| 3 | รอบเดียวจะเขียนเกิน 300 แถว → กักทั้งรอบ + แจ้ง IT (`flood`) | ของใหม่ที่หลั่งมาพร้อมกัน (เช่นเน็ตกลับมา) ที่ทำให้ผู้แจ้งเตือนท่วม |
| 4 | ปล่อยของที่กัก = คำสั่งแยก ระบุช่วง Device sequence, **dry-run ก่อนเสมอ** (จำนวน วันเก่าสุด/ใหม่สุด จำนวนต่อวัน) แล้ว `--confirm` | ปล่อยโดยไม่รู้ว่าจะกระทบรายงาน/การแจ้งเตือนของระบบอื่น |

คำสั่ง release จริง (แยก dry-run กับ `--confirm`) เป็นงานช่วง B ; `plan_release` คืนแผนล้วน ๆ ให้ทั้งสองโหมดใช้
ผู้ปล่อยต้องแจ้งก่อนว่าผู้แจ้งเตือนอื่นจะเห็นแถวที่ปล่อยเป็นแถวใหม่หรือไม่ (ADR 0002 ข้อ 6) ; แถวที่ปล่อยมีป้าย `SCAN-IMPORTER-RELEASED`

## ที่เก็บสถานะของ importer เอง
แยกจาก SQLite ของแอปแจ้งเตือน (ADR 0002 ข้อ 1): จุดล่าสุด และรายการที่กัก (เลข, เครื่อง, คนสแกน, เวลา, เหตุผลที่กัก, เวลาที่กัก, สถานะ ปล่อยแล้วหรือยัง)
ต้องคงอยู่ข้าม restart ของทั้งเครื่องสแกนและ importer เอง — นี่คือสิ่งที่ตัวเดิมไม่มี

## ลำดับการ restart บริการที่เกี่ยวข้อง
1. หยุด Scan importer 2. restart SQL Server เครื่องสแกน 3. เปิด Scan importer (จุดล่าสุดยังอยู่ จึงไม่เติมย้อนเอง) 4. ตรวจหน้า `/watch`
แอปแจ้งเตือนไม่ต้องหยุด ; ห้ามเปิด SCAN-WATCH (`sys_scan_watch.ENABLED`) กลับโดยไม่ผ่านการเพิ่ม age guard

## แผนย้ายผู้เขียน (ช่วง B)
1. **ตอนนี้ทำแล้ว:** SCAN-WATCH ปิด ; แอปแจ้งเตือนเฝ้า `old_rows` และ `unexpected_writer`
2. **B1 โหมดเงา:** importer ใหม่อ่านต้นทางแต่ไม่เขียน เทียบกับแถวที่ตัวเดิมเขียน ถอดกติกาเติมคอลัมน์ (Q26) ให้ตรงตัวเดิม — สังเกต: แถวของตัวเดิมเว้นคอลัมน์ `HR_*`/`SCAN_DATE`/`SCAN_TIME` ว่าง
   ส่วนแถวของ SCAN-WATCH เติมครบ ; ต้องยืนยันกับ HR ว่ารายงานใดอ่านคอลัมน์เหล่านั้น
3. **B2 ล้างข้อมูลซ้ำ:** HR ตัดสินกติกาเก็บ (767 คู่ SCAN-WATCH, 733 แถวเดิมซ้ำ) ; แอปนี้ออกรายการ ผู้ดูแลลบเอง แล้วใส่ unique index
4. **B3 สลับตัว:** หยุดส่วนนำเข้าของตัวเดิม → เปิดโหมด `write` (ห้ามสองตัวเขียนพร้อมกัน)

## การตัดสินใจ (8 พ.ย. 2569) และที่ยังต้องให้ HR/ผู้ดูแลตัดสิน (แอปนี้ไม่ลบหรือแก้ข้อมูล)
- **ตัดสินแล้ว:** SCAN-WATCH ปิดถาวร (ใช้ระบบของ Dev แทน) · แถวที่ SCAN-WATCH เติม 11,120 แถว (4 พ.ย. 4,556 + 8 พ.ย. 6,564) **เก็บไว้ ไม่แตะ** (ผู้ใช้ยืนยัน) ; รายงานย้อนหลังจะรวมแถวเหล่านี้
- ยังเปิด: กติกาเก็บแถวในกลุ่มซ้ำ
- กติกาเก็บแถวในกลุ่มซ้ำ ; ก่อนใส่ unique index ต้องไม่เหลือกลุ่มซ้ำ

## บัญชีฐานข้อมูล
ขั้นตอนสร้างบัญชีอ่านอย่างเดียวของแอป (MariaDB, SQL Server) และบัญชีเขียนของ importer: `docs/runbooks/db-accounts.md`

## ข้อควรระวัง
- แอปแจ้งเตือนต่อ MariaDB ด้วยบัญชี `root` (แม้ session READ ONLY) ควรเปลี่ยนเป็นบัญชี `SELECT` อย่างเดียว ; importer ใช้บัญชีของตัวเอง `INSERT` บน `fingle_scan` เท่านั้น
- query บน `MACHIN_SCAN_ID` โดยไม่มีดัชนีบนฐานจริงหนักมาก (เคยทำให้ query ค้างเกิน 3 นาที) — ใช้ช่วง `ID`/เวลาที่มีดัชนีเสมอ
