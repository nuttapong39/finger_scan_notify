# Scan importer: ผู้เขียนคนเดียว + กักแถวย้อนหลัง

สถานะ: **ออกแบบ + แกนตรรกะล้วนเสร็จ (8 พ.ย. 2569)** — ยังไม่เขียนฐานข้อมูลจริง (รอบัญชีเขียน MariaDB ที่จำกัดสิทธิ์เฉพาะ `fingle_scan` และการอนุมัติจาก HR)
ที่มา: เหตุการณ์ 8 พ.ย. 2569 ใน `docs/design/lost-scan-and-importer.md` · การตัดสินใจ: `docs/adr/0002-scan-importer.md` ข้อ 5–10
โค้ด: `finger_scan_notify/scan_importer/plan.py` (`plan_batch`, `plan_release`) · test: `tests/test_scan_importer_plan.py`

## ปัญหาที่ต้องแก้
1. **ผู้เขียนสองราย** เขียนแถวจากเครื่องสแกนลง `fingle_scan`: ตัวนำเข้าเดิม (`CWSMservice32.exe`, เก็บ `CommitTime` ถึงวินาที) และ `SCAN-WATCH` ของ HOSOffice ERP (เก็บ `TimeInout` ระดับนาที)
   ต่างกันที่ความละเอียดของเวลาและกันซ้ำด้วยเวลา จึงไม่เห็นแถวของกันและกัน → แถวซ้ำ (60 วัน: 767 กลุ่มคู่กับ SCAN-WATCH + 733 กลุ่มแถวเดิมซ้ำ)
2. **ไม่มีเบรกกันของเก่า:** หลัง restart SCAN-WATCH เติมสแกนย้อนหลัง 18 เดือนครั้งเดียว (6,564 แถว) และผู้แจ้งเตือนส่งการ์ดตามทุกใบ
3. ตัวนำเข้าเดิมดึงเฉพาะแถวล่าสุดและกันซ้ำด้วยเวลา จึงทำสแกนที่ใกล้กันหาย (Lost scan)

## หลักการ
- **ผู้เขียนรายเดียว:** มีเพียง Scan importer ตัวใหม่ที่เขียนแถวที่มี Device sequence ; ตัวเดิมและ SCAN-WATCH หยุดเขียน (SCAN-WATCH ปิดแล้ว และแอปแจ้งเตือนเฝ้า `unexpected_writer` ถ้ามันกลับมา)
- **กุญแจ = (`MACHIN_ID`, `MACHIN_SCAN_ID`)** ไม่ใช่เวลา: เขียนซ้ำเลขเดิม = ไม่เขียน (`INSERT … ON DUPLICATE KEY` ไม่เขียนทับ) ; **ไม่ใส่ unique index** (ตัดสินใจ 9 พ.ย. 2569: แถวซ้ำเดิมเก็บไว้ที่เดิมไม่แตะ ; กันซ้ำด้วยการเช็กกุญแจในโค้ด ซึ่งพอสำหรับผู้เขียนคนเดียว)
- **เวลาที่เก็บ = `CommitTime`** (ถึงวินาที ตรงกับแถวของตัวนำเข้าเดิมซึ่งเป็นแถวส่วนใหญ่ — 35,033 แถวตั้งแต่ ID 300000 — และเรียงเข้า-ออกในนาทีเดียวกันได้ถูก) สำรองด้วย `TimeInout` เมื่อ CommitTime ว่าง
- **ป้ายผู้เขียน:** `CREATE_BY='SCAN-IMPORTER'` (ปกติ) และ `'SCAN-IMPORTER-RELEASED'` (ปล่อยจากที่กัก) ให้ระบบอื่นแยกแถวย้อนหลังออกได้
- **ไม่เดา:** ไม่มีจุดล่าสุดที่บันทึกไว้ = หยุดรอคน ไม่เริ่มจากต้นตาราง

## วงจรต่อรอบ (ทุก ~2 วินาที)
1. อ่านต้นทาง `WHERE ID_TimeInout > จุดล่าสุด ORDER BY ID_TimeInout` เป็นชุด (SELECT อย่างเดียว ใช้ `tigersoft` เดิม)
2. อ่านกุญแจที่มีอยู่แล้วใน `fingle_scan` ของเลขช่วงนั้น (ข้อควรระวัง: `MACHIN_SCAN_ID` **ไม่มีดัชนี** ให้อ่านด้วยช่วงเวลา/ID ที่ใช้ดัชนีได้ ห้าม join/EXISTS ซ้อน)
3. `plan_batch(rows, existing_keys, now, checkpoint=…)` → `insert / held / duplicate / flood / needs_baseline / next_checkpoint`
4. เขียน `insert` ใน transaction เดียว ; บันทึก `held` ลงที่เก็บของ importer ; แล้วค่อยขยับจุดล่าสุดเป็น `next_checkpoint` (ขยับหลังบันทึกสำเร็จเท่านั้น)
5. `flood` หรือมี `held` ใหม่ หรือ `needs_baseline` → แจ้ง IT (ครั้งเดียวต่อเหตุการณ์) ด้วยกลไกเดียวกับ `scanwatch`

## ตัวป้องกัน 4 ชั้น
| ชั้น | กติกา | กันเหตุการณ์ใด |
|---|---|---|
| 1 | ไม่มีจุดล่าสุด → ไม่เขียนอะไร รอคนตั้งจุดเริ่ม (`needs_baseline`) | จุดหายตอน restart แล้วเติมทั้งตาราง |
| 2 | แถวเก่ากว่า 24 ชม. เวลาไม่ชัด หรือล้ำอนาคตเกิน 1 ชม. → **กัก** (`held`) ไม่เขียนเอง ; แถวไม่มีเวลาสแกนปล่อยไม่ได้ (`unreleasable`) | เติมย้อนหลังหลัง restart/เครื่องสแกนออฟไลน์ |
| 3 | รอบเดียวจะเขียนเกิน 300 แถว → กักทั้งรอบ + แจ้ง IT (`flood`) | ของใหม่ที่หลั่งมาพร้อมกัน (เช่นเน็ตกลับมา) ที่ทำให้ผู้แจ้งเตือนท่วม |
| 4 | ปล่อยของที่กัก = คำสั่งแยก ระบุช่วง Device sequence, **dry-run ก่อนเสมอ** (จำนวน วันเก่าสุด/ใหม่สุด จำนวนต่อวัน) แล้ว `--confirm` | ปล่อยโดยไม่รู้ว่าจะกระทบรายงาน/การแจ้งเตือนของระบบอื่น |

คำสั่ง release จริง (แยก dry-run กับ `--confirm`) เป็นงานช่วง B ; `plan_release` คืนแผนล้วน ๆ ให้ทั้งสองโหมดใช้
ผู้ปล่อยต้องแจ้งก่อนว่าผู้แจ้งเตือนอื่นจะเห็นแถวที่ปล่อยเป็นแถวใหม่หรือไม่ (ADR 0002 ข้อ 6) ; แถวที่ปล่อยมีป้าย `SCAN-IMPORTER-RELEASED`

## ที่เก็บสถานะของ importer เอง
แยกจาก SQLite ของแอปแจ้งเตือน (ADR 0002 ข้อ 1): จุดล่าสุด และรายการที่กัก (เลข, เครื่อง, คนสแกน, เวลา, เหตุผลที่กัก, เวลาที่กัก, สถานะ ปล่อยแล้วหรือยัง)
ต้องคงอยู่ข้าม restart ของทั้งเครื่องสแกนและ importer เอง — นี่คือสิ่งที่ตัวเดิมไม่มี

## ลำดับการ restart บริการที่เกี่ยวข้อง
1. หยุด Scan importer 2. restart SQL Server เครื่องสแกน 3. เปิด Scan importer (จุดล่าสุดยังอยู่ จึงไม่เติมย้อนเอง) 4. ตรวจหน้า `/watch`
แอปแจ้งเตือนไม่ต้องหยุด ; ห้ามเปิด SCAN-WATCH (`sys_scan_watch.ENABLED`) กลับโดยไม่ผ่านการเพิ่ม age guard

### B1 ผลถอดที่มา `HR_*` (9 พ.ย. 2569, 400 แถว/127 คน, อ่านอย่างเดียว ไม่พิมพ์ชื่อ)
- บัญชีอ่านของแอปเห็น `hr_person` แค่ 4 คอลัมน์ (`ID, FINGLE_ID, HR_FNAME, HR_LNAME`) และไม่มีตารางตำแหน่ง/แผนกอื่น → **สร้าง `HR_POSITION/DEP/DEP_SUB/PERSON_TYPE/LEAVEL_NAME` จากฐานนี้ไม่ได้**
- `FINGLE_ID` ของทุกแถวหาคนเจอ (400/400)
- `HR_FULLNAME` มีชื่อ+นามสกุลจาก `hr_person` ครบ 400/400 แต่ไม่เท่ากันตรง ๆ : 378 ลงท้ายด้วย "ชื่อ นามสกุล" (นำหน้าด้วยคำนำหน้า ซึ่ง `hr_person` ไม่มี) และ 22 แถวมีส่วนต่อท้ายอื่น
- ค่า `HR_*_NAME` ทั้ง 5 คอลัมน์คงที่ต่อคน (0 จาก 127 คนที่มีมากกว่าหนึ่งค่า)
- **ข้อสรุปการออกแบบ:** importer ใหม่คัดลอก `HR_*` จากแถวล่าสุดของคนเดียวกัน (`PERSON_ID`) ที่ตัวเดิมเขียนไว้ ; คนที่ไม่มีแถวเดิมเลย → กักแถวนั้นรอคนตัดสิน ไม่เดาคำนำหน้า/ตำแหน่ง ; ต้องมี test ครอบ (ยังไม่ทำ)
- ค้าง: ความหมาย `SCAN_TYPE` 0/1/4/5 ต่อเครื่อง และที่มาของแถว `IN`/`OUT` 3 แถว

### B1 ผลยืนยัน `SCAN_TYPE` (9 พ.ย. 2569, ผู้ใช้ให้ความหมาย + ตรวจเทียบเครื่องสแกน 400 แถว, อ่านอย่างเดียว)
- ความหมาย: `0` เข้างาน · `1` ออกงาน · `4` เข้างานพิเศษ · `5` ออกงานพิเศษ ; `IN`/`OUT` = สแกนผ่านมือถือในโปรแกรม HOSOFFICE (ไม่ใช่จากเครื่องสแกน)
- ที่มา: **`SCAN_TYPE` = คอลัมน์ `InOutMode` ของเครื่องสแกนตรง ๆ** (397/397 แถวตรงกันทุกคู่ 0→0, 1→1, 4→4, 5→5) ; หาแถวในเครื่องเจอครบ 400/400
- ข้อสังเกต: แถว `IN`/`OUT` 3 แถวมีเลข Device sequence ที่ตรงกับแถวของเครื่อง (`InOutMode`='1') → แถวเครื่องถูกทับ/ผูกกับการสแกนมือถือ ; ยังต้องถามผู้ดูแล HOSOffice ว่า "ผูก" อย่างไร (importer ใหม่ห้ามแตะแถวที่มีอยู่แล้ว กุญแจ (MACHIN_ID, MACHIN_SCAN_ID) กันไว้)
- งานถัดไป: ให้ `tigersoft` อ่าน `InOutMode` (`_normalise` → `mode`) แล้ว `plan` ส่งต่อเป็น `SCAN_TYPE`

### B1 ลงโค้ดแล้ว: ตัวสร้างแถว + เทียบทีละคอลัมน์ (9 พ.ย. 2569)
- `tigersoft` อ่าน `InOutMode` → `mode` ; `plan.build_row(src, person_id, template, consts)` สร้างแถว (กุญแจ, CommitTime, `SCAN_TYPE`, `DAY_TYPE_*`, ค่าคงที่, `HR_*` คัดลอกจาก template) หรือคืน None เมื่อสร้างไม่ได้ (ไม่มีเวลา / ไม่มี `PERSON_ID` / คนนั้นไม่มีแถวเดิม → ต้องกัก ไม่เดา)
- `FINGLE_ID` ใน hosoffice เป็น**ข้อความ** (เครื่องสแกนส่งตัวเลข) → เขียนเป็น `str` ; เวลาคลาดจาก CommitTime ได้ ≤ 2 วินาทีถือว่าตรง
- `shadow-report` ส่วนใหม่ เทียบแถวที่ importer ใหม่จะสร้างกับแถวจริง 400 แถวของตัวเดิม (ไม่แสดงค่า) : **เทียบได้ 385 · เหมือนทุกคอลัมน์ 383** · ที่เหลือ 2 แถวต่างแค่ `SCAN_TYPE` (แถว OUT จากมือถือ ซึ่งไม่ใช่งานของ importer) · 15 แถวไม่มีแถวอื่นของคนเดียวกันในตัวอย่างให้คัดลอก `HR_*` (ตัวจริงจะดึง template จากฐานข้อมูล ไม่ใช่จากตัวอย่าง)
- ค้างก่อนโหมดเขียน: ดึง template ต่อคนจาก hosoffice (query ต่อ `PERSON_ID` ใช้ดัชนี) · แถว `ID` (auto-increment?) · ตัวรันรอบ/transaction · บัญชี C

### B1 ดึงต้นแบบต่อคนจากฐานข้อมูล (9 พ.ย. 2569)
- `hosoffice.get_person_ids` (FINGLE_ID → `hr_person.ID`) และ `get_latest_rows_by_person` (แถวล่าสุดของตัวเดิมต่อ `PERSON_ID`, หนึ่ง query ต่อคน ใช้ดัชนี `(PERSON_ID, SCAN_DATE_TIME)`) ; `ID` ของ `fingle_scan` เป็น auto_increment → ไม่ต้องใส่
- ผลจริง: **เทียบได้ 400 · เหมือนทุกคอลัมน์ 397** · 3 แถวที่เหลือต่างแค่ `SCAN_TYPE` (แถว IN/OUT จากมือถือ) · ไม่มีแถวที่ขาดต้นแบบ

### หน้า Watch + โหมดเงาแบบสด (9 พ.ย. 2569)
- ตัดสินใจกับผู้ใช้: ควบคุมผ่านปุ่มบนหน้า `/watch` (ไม่ใช้คำสั่ง `manage.py release`) · รับให้เว็บถือบัญชีเขียน `scan_importer_rw` (SELECT, INSERT บน `fingle_scan` เท่านั้น) เมื่อถึงขั้นเขียนจริง · การสลับโหมดเงา→เขียนเป็นค่า `SCAN_IMPORTER_MODE` ใน `.env` + restart ไม่ทำเป็นปุ่ม
- ทำแล้ว (ยังไม่เขียน hosoffice): `scan_importer/runner.py` (รอบทุก 15 วินาที โหมด `off|shadow`) · ตาราง SQLite `importer_state`, `importer_held` · `routes_importer.py` : `GET /api/importer/status`, `POST /api/importer/baseline`, `GET /api/importer/release-preview` · การ์ด "Scan importer" บนหน้า Watch อัปเดตทุก 5 วินาที · ปุ่ม "ยืนยันปล่อย" ปิดอยู่จนกว่าจะมีโหมดเขียน
- ยังไม่มี: ตัวเขียนจริง (บัญชี C, transaction, ป้าย `SCAN-IMPORTER`/`-RELEASED`), ปุ่มปล่อยจริง + บันทึกว่าใครกด, โหมด `write` ใน settings

### ตัวเขียนจริง + ปุ่มปล่อย (9 พ.ย. 2569) — เขียนโค้ดและทดสอบแล้ว ยังไม่เคยเขียน hosoffice จริง
- `SCAN_IMPORTER_MODE=write` ต้องมี `HOSOFFICE_WRITE_USER`, `HOSOFFICE_WRITE_PASSWORD`, `SCAN_IMPORTER_COM_NAME`, `TIGER_*` ครบ ไม่งั้นแอปไม่เริ่ม (บอกชื่อค่าที่ขาด) ; รหัสผ่านเขียนไม่ปรากฏใน repr/log
- `hosoffice.insert_scan_rows` เป็นที่เดียวที่แอปเขียน hosoffice : บัญชีเขียนแยก, หนึ่ง transaction ต่อชุด (พลาดแถวเดียว = ย้อนกลับทั้งชุด), คอลัมน์จำกัดตามรายการ `INSERT_COLS`, ค่าส่งเป็นพารามิเตอร์, ติด `CREATE_BY`
- รอบเขียน : เขียนเฉพาะแถวที่ `plan_batch` ตัดสินว่า "เขียน" และสร้างแถวได้ครบ (หา `PERSON_ID` + ต้นแบบ `HR_*` เจอ) ; สร้างไม่ได้ = กักด้วยเหตุผล `no_person`/`no_template`/`no_time` ; ขยับจุดล่าสุดหลังเขียนสำเร็จเท่านั้น ; เกินเพดาน 300 = ไม่เขียนสักแถว
- ปล่อยแถวที่กัก (`POST /api/importer/release`) : เฉพาะโหมด write + ล็อกอิน ; ต้องส่ง `expect` เท่ากับจำนวนที่ตัวอย่างบอก (คำนวณใหม่ตอนสั่ง ไม่ตรง = 409 ไม่เขียน) ; ติดป้าย `SCAN-IMPORTER-RELEASED` ; บันทึก audit (ใคร เมื่อไร ช่วงเลข จำนวน) แสดงบนการ์ด ; สั่งซ้ำไม่เขียนซ้ำ
- ก่อนเปิดจริง : สร้างบัญชี C ตาม runbook, สำรองตาราง, ปิดตัวนำเข้าเดิมให้เหลือผู้เขียนคนเดียว, เปิด shadow ดูหน้า Watch ก่อน แล้วค่อยเปลี่ยนเป็น write + restart

### โหมดเงากักแถวที่สร้างไม่ได้ด้วย (9 พ.ย. 2569)
- โหมดเงาสร้างแถวแบบอ่านอย่างเดียว เพื่อให้เห็นก่อนเปิด `write` ว่ามีแถวที่สร้างไม่ได้เท่าไร : ไม่พบคนใน `hr_person` (`no_person`) หรือคนที่ยังไม่เคยมีแถวใน hosoffice จึงไม่มีต้นแบบ `HR_*` (`no_template`) — แถวเหล่านี้ถูกกัก ไม่เดา
- หน้า Watch แสดงจำนวนคนที่ต้องให้ HR ตรวจ/ลงแถวแรก (นับคน ไม่ส่งรหัสบุคคลออก) ; พอมีแถวแรกแล้ว ปล่อยแถวที่กักได้ในโหมด `write`
- ตัวอย่างจริง : พนักงานที่เริ่มงานวันที่ 9 พ.ย. 2569 สแกนครั้งแรกแล้วไม่มีผู้เขียนคนไหนเขียนลง hosoffice (Lost scan เลข 366008) — สาเหตุที่ตัวเดิมและ SCAN-WATCH ไม่เขียนยังต้องถาม HR/ผู้ดูแล HOSOffice

### นำเข้าตามเลขที่ระบุเอง (9 พ.ย. 2569)
- ใช้กับสแกนที่ตกหล่นก่อนจุดเริ่มต้น (เช่น Lost scan เลข 366008 ที่ตัวเดิมไม่เขียนเพราะข้อมูล HR ของพนักงานใหม่ยังไม่ครบตอนนั้น) : ผู้ดูแลระบุช่วงเลข (ไม่เกิน 200 เลขต่อครั้ง) บนหน้า Watch
- `GET /api/importer/manual-preview` (dry-run, อ่านเครื่องสแกนตรง ๆ, ข้ามเลขที่ hosoffice มีแล้ว, ไม่ส่งข้อมูลบุคคล) และ `POST /api/importer/manual-import` (ต้อง `expect` เท่าจำนวนในตัวอย่าง, เฉพาะโหมด write, ต้องล็อกอิน, ป้าย `SCAN-IMPORTER-MANUAL`, บันทึก audit `manual-import`)
- สแกนเก่ากว่า 60 วันไม่ทำ (ตรวจแถวซ้ำด้วยดัชนีเวลาไม่น่าเชื่อถือ) ; คนที่ข้อมูล HR ไม่ครบจะเขียนไม่ได้และแจ้งเลขในตัวอย่าง
- ใช้ได้เฉพาะโหมด write — เครื่องพัฒนาที่ยังอยู่โหมดเงาจึงยังนำเข้าเลข 366008 ไม่ได้ (ทำหลัง deploy หรือให้ลงในโปรแกรม HOSOffice เอง)

### ตรวจเจ้าของสแกน + ค้นหาที่ยังไม่เข้า hosoffice + เริ่ม importer ไม่ผูกกับ Monitor (9 พ.ย. 2569)
- **รายละเอียดต่อแถวก่อนยืนยัน:** ตัวอย่างนำเข้าตามเลขแสดง เลข, เครื่อง, เวลาถึงวินาที, ทิศทาง (เข้างาน/ออกงาน/พิเศษ จาก `scan_types.label`), `PERSON_ID`, ชื่อ (hr_person) และสถานะ (จะเขียน / มีแล้ว / เขียนไม่ได้ + เหตุผล) สูงสุด 50 แถว — แสดงบนหน้าที่ล็อกอินเท่านั้น ไม่บันทึกชื่อลง log/SQLite
- **ค้นหาที่ยังไม่เข้า hosoffice** (`GET /api/importer/missing?days=1..7`, อ่านอย่างเดียว ใช้ได้ทุกโหมด): อ่านเครื่องสแกนตามช่วงเวลา (`tigersoft.get_rows_between`) เทียบกุญแจ (เครื่อง, เลข) กับ hosoffice ; สแกนที่ใหม่กว่า 15 นาทีไม่นับ (ตัวเดิม/SCAN-WATCH เขียนช้ากว่าเครื่องสแกนเล็กน้อย) ; ผลเป็นภาพ ณ ขณะค้นหา
- **นำเข้าเฉพาะที่ขาด:** `manual-preview?seqs=…` และ `POST manual-import {seqs, expect}` (≤ 200 เลข, เลขที่ไม่ได้ระบุไม่ถูกแตะ) ตามเงื่อนไขเดิม: โหมด write เท่านั้น, ล็อกอิน, `expect` ต้องตรงตัวอย่าง, ป้าย `SCAN-IMPORTER-MANUAL`, audit
- **เริ่ม importer ตามโหมดของมันเอง** ไม่ผูกกับ `MONITOR_AUTOSTART` (`app.startup()`): Server รันโหมดเงาได้ก่อนวัน cutover โดยไม่ให้ Monitor ส่งแจ้งเตือนซ้ำกับเครื่องเดิม ; ตั้ง `write` ได้เครื่องเดียว (SERVER-SETUP หัวข้อ 9.1)
