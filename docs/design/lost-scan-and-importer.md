สถานะ: **ช่วง A และโค้ดช่วง C ลงมือแล้ว (8 พ.ย. 2569)** — ช่วง C ยังไม่เคยต่อ SQL Server จริง (รอผู้ใช้เปิดพอร์ต 1433 ของ .77 + ใส่ TIGER_PASSWORD ใน .env แล้วรัน `manage.py tiger-check`); ช่วง B รอบัญชีเขียน MariaDB และขั้นตอนเปลี่ยนตัว

## ปัญหา

## ข้อเท็จจริงที่ตรวจแล้ว (8 พ.ย. 2569, READ ONLY, ค่าสถิติรวมเท่านั้น)
- เส้นทาง: เครื่อง Tigersoft XFace100 → SQL Server `TigerWebServerPlus` บน 192.168.1.77 (instance บนเครื่อง `LZ-202306021404`)
  ตาราง `ZFP_TimeInOut` → `CWSMservice32.exe` (Delphi) → hosoffice `fingle_scan` (MariaDB 11.4 บน 192.168.1.250)
- `fingle_scan.MACHIN_SCAN_ID` = Device sequence (น่าจะเป็น `ZFP_TimeInOut.ID_TimeInout`) เรียงต่อกันข้าม 3 เครื่อง
  - 30 วัน: 5,400 เลขจากช่วง 5,416 → **หาย 16 เลข ทั้งหมดตั้งแต่ 3 พ.ย.** (ก่อนหน้าไม่หายเลย)
  - 14/16 หายทีละ 1 เลข โดยสแกนข้างเคียงห่าง ≤ 60 วินาที; 11/16 ช่วง 16:00 น.
- **ต้นเหตุ** (ข้อความ SQL ใน `CWSMservice32.exe`): ทุกรอบอ่าน `SELECT TOP 1 * FROM ZFP_TimeInOut ORDER BY ID_TimeInout DESC`
  แล้วเช็กซ้ำด้วย `fingle_scan WHERE SCAN_DATE_TIME='…'` → สแกน ≥ 2 ครั้งในรอบเดียว แถวก่อนหน้าหาย,
  สองคนสแกนวินาทีเดียวกัน คนที่สองหาย
- 4 พ.ย.: 115 Device sequence ถูกนำเข้าซ้ำ (คนเดิม เวลาต่างกัน 2–65 วินาที สำเนาหนึ่งวินาที = 00)
- อินเทอร์เน็ตไปยังเครื่องสแกนล่มราว 1 วัน (4–5 พ.ย.) — 303 Scan ของผู้มี token ช่วงนั้นแอปเราไม่ได้จัดการ (ยังไม่รู้สาเหตุ ตรวจในช่วง A)
- แถว FACESCAN ไม่มีรูป/คะแนนใบหน้า/เวลาบันทึก (`DATE_TIME_SAVE`) — มีเฉพาะแถว SIGN จากแอป
- `fingle_scan.ID` ไม่เรียงตามเวลาสแกน (109 ครั้ง/30 วัน, 48 ครั้งช้ากว่า 3 ชม. — ส่วนใหญ่ MANUAL)
- `work_checkinout` = ระบบเก่า (ล่าสุด ก.พ. 2025) ไม่เกี่ยว; `sys_scan_agent`/`fingle_scan_raw` มีโครงแต่ว่าง

## ช่วง A — แอปนี้ (ใช้ hosoffice อย่างเดียว)
1. **ตัวตรวจ Device sequence**: ทุก 60 วินาทีอ่าน `MACHIN_SCAN_ID` ของแถวจากเครื่อง (ไม่รวม MANUAL/SIGN) ช่วงล่าสุด
   หาเลขที่ขาด → บันทึกเป็นเหตุการณ์ใน SQLite (เลข, เวลาของสแกนก่อน/หลัง, เห็นครั้งแรก, ปิดเมื่อ — ไม่มีเครื่อง เพราะแถวที่หายไม่มีข้อมูลนั้น; ช่วง C จะบอกเครื่อง/ชื่อ)
   ขาดเกิน 15 นาที = Lost scan → แจ้ง IT; เลขที่ถูกเติมภายหลัง → ปิด + แจ้งกลับมาปกติ; สรุป 07:30 ถ้ายังค้าง
2. **Import stall**: เวลาที่เห็น Device sequence ใหม่ล่าสุด (แอปจดเอง เพราะ FACESCAN ไม่มีเวลาบันทึก)
   ใช้ตัดสินตามช่วงเวลาใน Q20 → ตัวเตือนยังไม่สแกนงดรอบนั้นและลองใหม่ทุกรอบ, แจ้ง IT ครั้งเดียวต่อเหตุการณ์
3. **การแจ้ง IT**: Flex card "แจ้งเตือนระบบ" ส่งผ่าน delivery เดิมถึง Person token ของ IT alert recipient (ตั้งค่าได้ ค่าเริ่ม 156)
   ไม่นับเป็นโควตาของการแจ้งเตือนสด, บันทึกด้วย Send source ใหม่
4. **หน้า "Scan ที่อาจตกหล่น"** (Dashboard, ต้องล็อกอิน): เหตุการณ์ Lost scan/Import stall + สถานะการนำเข้า
   + หัวข้อ "นำเข้าซ้ำ" (คู่แถวที่ Device sequence ซ้ำ: ID, ชื่อ, เวลาสองค่า) สำหรับ HR
5. **Monitor อ่านซ้ำช่วงล่าสุด**: นอกจาก `ID > last_scan_id` ให้อ่านแถวที่ ID อยู่ในช่วงย้อนหลังเล็ก ๆ ที่ยังไม่มีทั้ง log และ skip — กันส่งซ้ำด้วย `scan_id` เดิม
6. **ตรวจ 303 Scan 4–5 พ.ย.** ว่าทำไมไม่มีทั้ง log และ skip แล้วแก้ถ้าเป็นบั๊กของแอป

### ต่างจากแผนระหว่างลงมือช่วง A
- **เกณฑ์ Import stall ใช้ "จำนวนสแกนที่ปกติควรมาในช่วง since→now" แทนช่วง 20 นาทีคงที่**: ข้อมูลจริงช่วง 09:00–12:00 แทบไม่มีสแกน
  (เฉลี่ย 0.2 ต่อ 20 นาที) การนับ "เงียบ 20 นาที" ตรง ๆ จะงดการเตือน 09:30 ผิด ๆ ทุกวัน และจับไม่ได้ว่าตัวนำเข้าตายตั้งแต่ 08:05
  ตอนนี้: เงียบ ≥ 20 นาที **และ** ในวันทำงานก่อนหน้า ช่วงนาฬิกาเดียวกันนั้น (ตั้งแต่เห็นเลขใหม่ล่าสุดถึงตอนนี้ ข้ามเที่ยงคืนได้) เฉลี่ยมี ≥ 3 สแกน
  ยังจำกัดเฉพาะช่วงเฝ้าตาม Q20 และเริ่มตรวจครั้งแรกใช้เวลาของสแกนล่าสุดจริง (เปิดแอปหลังข้อมูลหยุดแล้วก็จับได้ทันที)
- ตรวจทุก 60 วินาที (แผน 5 นาที) — query เบา (0.4 วินาที/รอบ); เกณฑ์แจ้งยังเป็น 15 นาที
- แถวนำเข้าซ้ำนับด้วย (เครื่อง, Device sequence) — ย้อน 60 วันพบ **733 เลข (1,466 แถว)**: 618 เลขเมื่อ 2–6 ต.ค. และ 115 เลขเมื่อ 4 พ.ย.
  (ตอนวิเคราะห์ย้อน 30 วันเห็นแค่ 115) → การนำเข้าซ้ำเกิดอย่างน้อยสองครั้ง
- การแจ้ง IT บันทึกเป็น guard event `it_alert` (ไม่ใช่ notify_logs/Send source) เพราะไม่ใช่ Scan ของบุคลากร และไม่นับโควตา
- ผู้รับแจ้ง IT ตั้งได้ที่หน้า "Scan ที่อาจตกหล่น" (ค่าเริ่มต้น person_id 156)
- ช่องว่างใหญ่กว่า 100 เลขถือเป็นเลขกระโดด/เริ่มนับใหม่ ไม่เปิดเหตุการณ์ (กันท่วม); เหตุการณ์ที่เลื่อนพ้นหน้าต่าง 2,000 เลขถูกปิดโดยไม่ประกาศ "กลับมาปกติ"
- เงียบข้ามวัน (เช่น หลังวันหยุด): ประเมินจาก 20 นาทีล่าสุดของวันนี้เท่านั้น (ไม่นับหางของเมื่อวาน) กันแจ้งผิดก่อนคนมาทำงาน
- แจ้ง IT ไม่สำเร็จ: พัก 3 นาทีก่อนลองใหม่ บันทึกชั่วโมงละครั้ง; สรุปเช้าส่งได้ถึง 10:30 เท่านั้น (restart ตอนบ่ายไม่ส่ง)
- **แจ้งครั้งแรกหลัง deploy:** Lost scan ที่ค้างอยู่ในหน้าต่าง (เช่น 16 เลขตั้งแต่ 3 พ.ย.) จะถูกแจ้งรวมเป็นการ์ดเดียวหลังตรวจครั้งแรก 15 นาที — ตั้งใจให้ IT เห็นรายการที่ค้างทั้งหมด
- ตัวเฝ้าและแถวที่ MySQL ให้มาใช้เวลาแบบ naive ของเครื่องเดียวกัน — ต้องอยู่เขตเวลาเดียวกัน (Asia/Bangkok) ซึ่ง preflight.sh ตรวจอยู่แล้ว
- Monitor อ่านซ้ำ ID ย้อนหลัง 300 แถวเฉพาะคนที่มี token ที่ยังไม่มีทั้ง log และ skip (ถ้าดึงไม่ได้ข้ามรอบนั้น ไม่ทำให้รอบหลักล้ม)

### ผลตรวจ 303 Scan วันที่ 4–5 พ.ย. (ข้อ 6)
ไม่ใช่บั๊กในโค้ดปัจจุบัน: Monitor บนเครื่อง Windows ไม่ทำงานตั้งแต่ปลาย 4 พ.ย. จนเริ่มใหม่ 6 พ.ย. 06:53 ตอนเริ่มใหม่มันข้าม scan เก่ากว่า 180 นาที
ประมาณ 1,234 แถว (ID 338924–340157) ตามกฎ แต่ตาราง `scan_skips` ว่าง — โปรเซสที่รันอยู่เป็นโค้ดรุ่นก่อนเพิ่มการบันทึกการข้าม
(ยังไม่ได้ restart) จึงไม่มีร่องรอยว่าถูกข้าม · เหตุที่เหลือคือ **ไม่มีใครรู้ว่า Monitor หยุด** — การเฝ้า process ตาย ต้องมีตัวภายนอก (systemd บน Server หลัง cutover)

## ความเสี่ยง
- กฎเติมคอลัมน์ไม่ตรงตัวเดิม → รายงาน HR เพี้ยน: กันด้วยโหมดเงาและ test จากข้อมูลจริง
- สองตัวเขียนพร้อมกันช่วงเปลี่ยนตัว → แถวซ้ำ: unique index + ขั้นตอนเปลี่ยนตัวที่ห้ามซ้อน
- `ID_TimeInout` (IDENTITY) commit ไม่เรียงเหมือนกัน → การตรวจเทียบ 24 ชม. เติมให้
- แจ้ง IT ท่วม → ครั้งเดียวต่อเหตุการณ์ + สรุปรายวัน
