# 0002 — Scan importer แยก process และใช้ Device sequence เป็นกุญแจ

สถานะ: ยอมรับ (8 พ.ย. 2569)

## บริบท
ตัวนำเข้าเดิม (`CWSMservice32.exe`) อ่าน `ZFP_TimeInOut` ของเครื่องสแกนทีละแถวล่าสุด (`TOP 1`) และเช็กซ้ำด้วยเวลา
จึงทำ Scan หายเมื่อสแกนใกล้ ๆ กัน (Lost scan) ไม่มีซอร์สให้แก้ ทีม IT ตัดสินใจเขียน Scan importer ใหม่ด้วย Python
แอปแจ้งเตือนนี้ถูกออกแบบให้อ่าน hosoffice อย่างเดียว (บังคับ `READ ONLY` ทุกการเชื่อมต่อ) และทำงานเป็น process เดียว (ADR 0001)

## ตัดสินใจ
1. Scan importer อยู่ใน repo เดียวกัน (`scan_importer/`) แต่เป็น **process แยก** (systemd unit, `.env`, บัญชีฐานข้อมูลของตัวเอง)
   แอปแจ้งเตือนยังอ่าน hosoffice อย่างเดียวเหมือนเดิม — ไม่มีโค้ดเขียน hosoffice ในแอปแจ้งเตือน
2. **Device sequence (`MACHIN_SCAN_ID` = `ZFP_TimeInOut.ID_TimeInout`) เป็นกุญแจ** ของการนำเข้า:
   ดึงตามเลข (ไม่ใช่ตามเวลาหรือแถวล่าสุด), ขยับจุดล่าสุดหลังบันทึกสำเร็จ, กันซ้ำด้วย unique index บนเลขนี้
   ทำให้รันซ้ำ เติมย้อนหลัง และตรวจเทียบได้โดยไม่เกิดแถวซ้ำ
3. บัญชีเขียนของ Scan importer มีสิทธิ์ `INSERT` บน `fingle_scan` เท่านั้น (+ `SELECT` ตารางอ้างอิง) ไม่ใช้ root
4. ค่าที่เขียนต้องตรงกับตัวเดิมทุกคอลัมน์ และเปลี่ยนตัวผ่านโหมดเงาก่อนเสมอ
5. **ห้ามนำเข้าย้อนหลังเองหลัง restart/เริ่มใหม่:** ตัวใหม่เริ่มจากจุดล่าสุดที่บันทึกไว้เท่านั้น ถ้าจุดนั้นหาย ให้หยุดและรอคน
   ไม่เดาว่าต้องเริ่มจากต้นตาราง
6. **การเติมย้อนหลังเป็นคำสั่งแยกที่คนสั่งเอง** (ระบุช่วง Device sequence, มี dry-run แสดงจำนวนและช่วงวันที่ก่อนเขียน)
   และต้องแจ้งก่อนว่าผู้แจ้งเตือนอื่น (เช่นตัวเฝ้าของ HOSOffice ERP) จะเห็นเป็นแถวใหม่หรือไม่
7. ผู้แจ้งเตือนทุกตัวที่ทำงานตามแถวใหม่ต้องมี age guard (แอปนี้ 180 นาที) — ตัวเฝ้าของ HOSOffice ERP v2.20.74 ไม่มี จึงต้องปิดไว้จนกว่าจะเพิ่ม
8. **ผู้เขียนแถวจากเครื่องมีรายเดียว:** Scan importer ตัวใหม่เท่านั้น ; ตัวนำเข้าเดิมหยุดส่วนนำเข้า และ `SCAN-WATCH` ของ HOSOffice ERP ปิดถาวร
   (เก็บเวลาคนละความละเอียดกับตัวเดิมและกันซ้ำด้วยเวลา จึงเกิดแถวซ้ำ) ; ป้ายผู้เขียน `CREATE_BY='SCAN-IMPORTER'` / `'SCAN-IMPORTER-RELEASED'`
   แอปแจ้งเตือนเฝ้า `unexpected_writer` : ถ้ามีแถวใหม่จากผู้เขียนที่ปิดแล้ว แจ้ง IT ทันที
9. **เวลาที่เก็บ = `CommitTime` (ถึงวินาที)** สำรอง `TimeInout` ; **กุญแจกันซ้ำ = (`MACHIN_ID`, `MACHIN_SCAN_ID`)** ไม่ใช่เวลา
10. **กักแถวเก่า:** แถวต้นทางที่เก่ากว่า 24 ชม. ไม่เขียนเอง (กัก `held`) ; รอบเดียวเขียนเกิน 300 แถว = กักทั้งรอบ + แจ้ง IT ; ปล่อยด้วยคำสั่งแยกที่มี dry-run
    แกนตรรกะอยู่ที่ `scan_importer/plan.py` (ล้วน ไม่มี I/O) ดู `docs/design/scan-importer-single-writer.md`

## ทางเลือกที่พิจารณา
- **ใส่การนำเข้าในแอปแจ้งเตือน**: deploy เดียว แต่ทำลายหลัก "อ่าน hosoffice อย่างเดียว" และถ้าแอปแจ้งเตือนล่ม การนำเข้าเวลาทำงานล่มด้วย — ไม่เลือก
- **repo แยก**: แยกขาด แต่คำศัพท์และกฎ Device sequence ต้องดูแลสองที่ — ไม่เลือก
- **ดึงตามเวลา (`CHECKTIME > เวลาล่าสุด`)**: ทำหายเมื่อเวลาซ้ำ/นาฬิกาเพี้ยน — ไม่เลือก
- **รันบนเครื่อง .77 (Windows)**: ไม่ต้องเปิด firewall แต่ดูแลแยกจากชุด deploy ของทีม — ไม่เลือก

## ทำไมข้อ 5–7 (เหตุการณ์ 8 พ.ย. 2569)
หลัง restart SQL Server ของเครื่องสแกน ตัวเฝ้าของ HOSOffice ERP (`SCAN-WATCH`, `CREATE_BY='SCAN-WATCH'`) เติมแถวเก่า 6,564 แถวเข้า `fingle_scan` ในคราวเดียว
(ชุดแรก 4,556 แถวเมื่อ 4 พ.ย.) แล้วส่งการ์ด "ลงเวลาสำเร็จ" ตามให้บุคลากรหลายร้อยใบ (คนหนึ่งได้ 56) แม้ข้อมูลที่เติมจะเป็นสแกนจริง
และเพราะมันเก็บเวลาระดับนาทีส่วนตัวนำเข้าเดิมเก็บถึงวินาที สองรายจึงไม่เห็นแถวของกันและกัน เกิดแถวซ้ำ 767 กลุ่ม
(อีก 733 กลุ่มเป็นแถวเดิมสองแถว) รายละเอียดและหลักฐานใน `docs/design/lost-scan-and-importer.md`
แอปแจ้งเตือนมีตัวตรวจ `check_old_rows` เป็นด่านสุดท้ายที่แจ้ง IT ภายในหนึ่งนาที แต่ผู้เขียนต้องเหลือรายเดียวและต้องไม่ก่อเหตุเองตั้งแต่ต้นทาง

## ผลที่ตามมา
- ต้องล้างแถวที่ Device sequence ซ้ำก่อนใส่ unique index (60 วันล่าสุด 1,500 กลุ่ม: 767 คู่กับ SCAN-WATCH + 733 แถวเดิมซ้ำ) — HR ตัดสินกติกาเก็บก่อน ผู้ดูแลลบเอง
- ต้องเปิดพอร์ต SQL Server ของ .77 ให้ dashboard-srv และมีบัญชีฐานข้อมูลเพิ่มสองบัญชี (อ่านเครื่องสแกน, เขียน Scan importer)
- deploy kit ต้องรองรับสอง unit บนเครื่องเดียว; การ restart แอปแจ้งเตือนไม่กระทบการนำเข้า และกลับกัน
- แถวจากคำร้องลืมสแกน (MANUAL) และแอปลงชื่อ (SIGN) ไม่มี Device sequence — ไม่ผ่าน Scan importer
